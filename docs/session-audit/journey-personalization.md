## 1. What it is

### 1a. The personalization spine (`src/lib/personalization/spine.ts`, 651 lines, merged)

- A list `SIGNALS` of about 42 questions. Each has: `field` (where stored), `group` (who, want, how, situation,
  proof), `needs` (which of the 11 journeys and which stages ask it, plus an optional `when` rule), `drives` (plan,
  learning, networking, opportunities, report, coaching, each with a sentence), `opportunity` (what it can open) and
  `readBy` (files that must mention the field).
- `spineFor(journey, stage, profile)`, `spineGaps(...)` (the unanswered ones, with `why`, `unlocks`, `href`) and
  `spineProgress(...)`.
- Rule enforced by test `src/test/personalization-spine.test.ts`: each `readBy` file must exist and mention the field.
- Journey sets: `SEARCHING` (7 journeys) and `NOT_SEARCHING` (GROWING, ENTREPRENEUR, FRACTIONAL, TIME_OFF).
- Consumers in code: only `src/lib/journey/engagement-data.ts` and `engagement.ts`. They take the first gap and
  add it to the "unlock steps" and to a plan item ("Answer one question that sharpens your plan: ..."). Nothing else
  in `src/` imports `spine.ts` (the spine is not the source for Improve your search or any strip).
- Known weakness, already stated in `docs/personalization-audit/questions.md`: the `readBy` test passes on files that
  only check "was it answered", so the spine overclaims (blockers, progress pace, motivations, willing to start lower).

### 1b. Job-matching personalization (merged, from the job-board work)

| File | What it does | Used by |
|---|---|---|
| `signals.ts` | 7 matching signals (city, title, function, tools, industries, work setup, clearance) with weights summing to 100, real payoff counts, and "Your search is X% tuned" | `KnowYouCard`, `KnowYouSection`, the Improve page, `redesign/tailored.ts` |
| `match-inputs.ts` | `MATCH_INPUT_FIELDS`: the 45 profile fields job matching reads; `sameMatchInputs` | retune, snapshots |
| `match-compute.ts`, `match-snapshot.ts`, `match-verdict.ts` | Run matching, keep a snapshot, diff verdicts before and after | retune |
| `retune.ts` | `runRetune(profile, trigger)`: before and after match counts on today's jobs, top reasons, event `search_retuned`. Triggers: city, tools, clearance, industry, search_strategy, resume, dismiss | `retune-actions.ts`, `RetuneMoment` used by 10 components (`AddCityPrompt`, `ToolsChecklist`, `SearchStrategyForm`, `ResumeUploadForm`, and others) |
| `smarter.ts` | "Your board got smarter" lines, only when something real changed | `KnowYouSection`, Job Search Daily |
| `why-this-job.ts` | Up to three fit reasons and one honest gap per job | `DiscoverJobCard`, find-my-job |
| `resume-readback.ts` | Read-back of what was parsed from the résumé | `ResumeReadback` |
| `blocker-step.ts` | Turns "what gets in the way" into the first plan step, and "what drives you" into the Home note reason | `home-note.ts` (committed), `dashboard/page.tsx` (uncommitted) |

The owner's honesty rule is in the code: retune numbers are computed, never estimated, and the step list is bound to
the server action's pending state with no timers.

### 1c. `PersonalizationQuestion` (branch only)

- 66-line presentational component. Props: `id`, `question`, `payoff`, `optional`, `pending`, `htmlFor`, `badge`,
  `children`, `className`.
- Renders a card with a heavy border: a black "Personalize" pill, optional "Optional, takes a few seconds", the
  question as the largest text, then "What you get: <payoff>", then the answer controls. `pending` sets `cursor-wait`
  (matches design-principles rule 2).
- Applied on the branch to 33 questions: `SearchStrategyForm` (about 24), `PersonalContextForm` (9),
  `SkillsAssessmentForm` (4), `PeopleEnergyQuestion` (1) and `ConfidenceSlider` (optional payoff).
- Payoffs are static strings, written by hand, one per question. No receipt, no step counter, no live update.

### 1d. Journey and menu rules (merged)

- `src/lib/journey/journey.ts`: `JourneyType` has 11 values (LAID_OFF, EXPLORING_MOVE, GROWING, PROMOTION,
  CAREER_CHANGE, STUDENT_NEW_GRAD, RETURNING, NEXT_ACT, ENTREPRENEUR, FRACTIONAL, TIME_OFF); 7 stages.
- `src/lib/journey/menu.ts`: 7 menu modes (EXPLORING, PREPARING, ACTIVE, STAYING, LANDED, PORTFOLIO, LEAVE), 10
  pillars, per-item show, locked or hide rules (`MENU_RULES`), `statusUnlock` ("Turn on more tools" box), and a
  phone bottom bar `MOBILE_TAB`. `menuMode(stage, journey)` maps the 11 journeys to the 7 modes.
- `src/lib/journey/apply.ts` now sets `isPivoting = true` when the journey becomes CAREER_CHANGE (found; this fixes
  a gap the alignment audit and `journeys.md` both list).
- Plan, playbook, engagement, win-back, auto-advance (Landed to Managing after 90 days), sponsored seats: merged or
  in HEAD; not re-read in detail.

## 2. How it fits the redesign

### 2a. Does `PersonalizationQuestion` fit the question-bundle design?

Partly. It is a good single question, not a bundle.

| Bundle rule (`bundles.md`) | Component today | Verdict |
|---|---|---|
| Payoff first ("why we ask") | Yes, "What you get" sits under the question, before the controls | Fits |
| Payoff shown the moment it is answered / updates as you answer | No: static text | Gap |
| At most three per bundle, 2 to 3 at a time | One card per question; `SearchStrategyForm` stacks about 24 of them on one page | Contradicts the rule if used as-is |
| Receipt after (before and after, places changed, tuned %, next bundle) | Nothing | Gap (nothing to attach to) |
| Honest payoff only ("no honest payoff, no question") | Text is hand-written and not checked against code | Risk (see 3a) |
| One note per page, at most three sections (page contract) | Every question is a bordered `border-2` card | Contradicts if many on a page |
| Dark navy only for the one unlock moment; one action colour | Uses black pill and neutral border on purpose; accent kept for answer buttons | Fits |
| Names say the benefit; "Personalize" place is replaced | The pill says "Personalize" on every card | Wording to decide: the place goes, the word is still an owner term |
| Keyboard and label (design principles) | `htmlFor` label support, `aria-labelledby` section | Fits |

### 2b. Can it be the building block?

Yes, as the inner unit of a bundle, not as the page. The real building blocks the redesign needs already exist in
other places:

- Receipt data: `runRetune` / `RetuneView` (real before and after counts) and `smarter.ts` lines. These are the only
  honest receipt engine in the code. `src/app/dev-preview/_mockups/questionnaire.tsx` has mock `TuneQuestion`,
  `TuneDone`, `ReceiptHome`, `ReceiptNetwork` (sample data only).
- "Tailored for you" rows: `src/lib/redesign/tailored.ts` plus `https://launchyournextchapter.com/dashboard/improve`
  (committed, behind the redesign flag).
- Gap picker: `spineGaps` already returns "the next question, with why and what it unlocks". It could choose the
  "one optional next question" the owner asked for.

Suggested shape (not built):

- `QuestionBundle` (new): header with "why we ask" and `1 of 3`, a list of `PersonalizationQuestion` children (max 3),
  a live payoff line fed by the answers, a submit that runs the save and then the receipt.
- `Receipt` (new, shared): `RetuneView` for kind A, a plan or tone preview for kind B, people for kind C.
- `PersonalizationQuestion` changes: make `payoff` a function of the current answer or accept a `ReactNode` that
  updates; add `step`/`of`; drop the heavy border when inside a bundle (the bundle is the card); keep `pending`,
  `htmlFor`, `optional`; rename the pill from "Personalize" to the strip name ("Better jobs for you") passed as a prop.
- Move it from `src/components/ui/` only if the owner wants it to stay a primitive; the redesign components live in
  `src/components/candidate/`.

## 3. Conflicts

### 3a. With the audit findings and bundles

1. **Payoff text promises things the audit says nothing reads.** On the branch:
   - motivations: "Your coach calibrates how they talk to you" while `bundles.md` H3 says motivations should change
     the Home note (it now does through `noteWhyWithMotivation`, so the payoff is outdated in the other direction);
   - consistency self-rating: "Your weekly plan is sized to how consistent you really are"; `questions.md` row 116
     says coach panel only (UNCLEAR, default drop);
   - "How do you like to make progress": "Your weekly plan is sized to your pace"; row 121 says no plan code reads it
     and it is merged into pace and push;
   - follow-up on applications: "Your coach can plan follow-up notes"; `OPEN_ITEMS.md` and the alignment audit say
     zero reads;
   - barriers: "Your Search Strategy guidance goes after the barriers you name first"; rows 114 and 115 say the report
     text reads it, scoring excludes it.
   Under the owner's rule these would be dropped or re-worded. The component makes unproven promises look official.
2. **Victoria and "your coach" in payoffs.** `bundles.md` decision: Victoria's chat replies are out of scope for now;
   a payoff that says "Victoria adjusts" must read "the one note on Home". About 6 branch payoffs name Victoria or the coach.
3. **Blockers and motivations: this work answers a flag in my audit.** `questions.md` and `bundles.md` H2 and H3 say
   "no plan code reads blockers or motivations; to build". `blocker-step.ts` (with tests) builds both: first step of the
   week from the top blocker, and the Home note reason from motivations. Status: motivation line wired in
   `home-note.ts` (committed); plan step wired only in the uncommitted `dashboard/page.tsx` edit. `docs/what-you-asked-for.md`
   item 30 says "built, not wired" and is now partly stale. H2 and H3 can be marked "built, wire and commit".
4. **Career change and `isPivoting`.** `journeys.md` says career change is not wired to the pivot tools. `apply.ts`
   sets `isPivoting = true` on that journey and `engagement-data.ts` reads `targetFunction`. Partly answered; the
   target field question and step-down answer are still not found as stored fields.
5. **Venture field.** `journeys.md` proposes "venture (new)" for Entrepreneur. `journeyDetails.venture` already exists
   (written in `privacy/actions.ts`, shown in `JourneySelector.tsx`), but the alignment audit says nothing reads it.
   Bundle O1 should say "reuse the existing field, then make the plan read it", not "add".
6. **Return date, fractional offer, open days, engagement end** already exist in `journeyDetails` and the plan reads
   them (alignment audit section 2). Bundle O1 "return date [30]" is therefore a keep, not new.
7. **Spine vs the audit's keep and drop list.** The spine still lists questions the audit drops or merges: coaching
   style asked in several places, `willingToFollowUpOnApplications`, benefits priorities. Spine is the "ask" list the
   engagement code uses for the next-question prompt, so a dropped question could still be offered by `spineGaps`.
   Spine `needs` must be edited together with each drop, or the plan will keep asking.
8. **Spine groups differ from strips.** Spine groups (who, want, how, situation, proof) and drives (plan, learning,
   networking, opportunities, report, coaching) do not map to the strips (Home, Jobs, Network, Learn) or to the
   bundle ids (O1 to O6, H1 to H5, J1 to J7, N1 to N6, L1 to L6). Two sources of truth for "what is asked where".
9. **Unread instruments.** The spine now covers Track Record, What I Need, Work Interests and the coaching form
   (commit 122bdc5a), but the alignment audit still lists 7 Track Record fields and about 16 What I Need items as
   unread. `bundles.md` "pending your decision" is unchanged; this work does not decide it.
10. **Receipt kind A coverage.** The 45 `MATCH_INPUT_FIELDS` limit what a before and after can show (already in
    `bundles.md`). `RetuneTrigger` has 7 values (city, tools, clearance, industry, search_strategy, resume, dismiss);
    bundles J2 to J7, H, N and L need new triggers or a generic "fields changed" trigger, not found today.
11. **Two "tuned" numbers.** `signals.ts` gives "X% tuned" for 7 matching signals; `spineProgress` gives done of total
    for the journey questions. The redesign wants one tuned % on each strip. They must be one number per strip or
    be named differently.

### 3b. With the redesign rules (`docs/candidate-redesign.md`)

- "A change that adds a card ... must say what it removes": the branch wraps 33 existing fields, so it adds no new
  fields, but it adds a heavy card around each, which fights the three-section contract on the Search Strategy page.
- "Every question flow: two or three at a time, why we ask first, payoff updating as you answer, a finish screen":
  the branch does the first half only.
- "Every claim says why": the payoff line is the "why", but unverified (3a-1).
- Page contract "one primary action": each `PersonalizationQuestion` section has its own controls; there is no single
  primary action per screen.
- Design rule "Never disable a button without explaining": not touched by the component.
- Branch touches `SearchStrategyForm.tsx` (530-line diff). `docs/candidate-redesign.md` sends changes through
  `src/app/dev-preview/` first and screenshots; the branch has no preview. Not found: any dev-preview of
  `PersonalizationQuestion`.
- Merge risk: the branch is based on a main of 15 Oct; `SearchStrategyForm` is also in the 45-field retune path and
  Home's "Search details" tab. Expect conflicts with any redesign edit of those forms.

## 5. New ideas

1. **One registry, three views.** Generate the bundles, the spine and the strips from one list: each entry has bundle
   id, strip, journeys, stages, field, payoff kind (A to D), and `readBy`. Keep the existing `readBy` test and add
   "the payoff text comes from a function that reads the field", so the payoff cannot lie.
2. **Use `spineGaps` as the "one optional next question"** at the end of each receipt; it already returns why and
   what it unlocks, and is journey-aware, so non-search members never get a job-search question.
3. **Journey-aware strips.** For the 4 non-search journeys, the Jobs strip becomes the journey's own strip
   ("Know your worth" for Growing; "Your pipeline" for Fractional; "Your way back" for Time off; "Your venture" for
   Entrepreneur). The spine's `NOT_SEARCHING` and `SEARCHING` sets already split them.
4. **Generic retune.** Let `runRetune` take any list of changed `MATCH_INPUT_FIELDS` so every kind-A bundle gets a real
   receipt with no per-page trigger.
5. **Receipt from `smarter.ts`.** Reuse "Since you X on <date>: 111 to 261 matches" as the receipt line, and as the
   Home one-note line a week later.
6. **Mark each payoff with its proof state** in code (`proven`, `to build`, `coach only`), and fail the build if a
   `to build` payoff is shown.
7. **Blocker step for the 4 weakest journeys.** `BLOCKER_STEPS` is job-search flavoured (for example "send one short
   message"); add journey variants (Time off: "block two hours for a skills refresh") before wiring to everyone.
8. **Time as personalization.** Playbook clocks (weeks 3, 6, 9, 13 per `CANDIDATE_JOURNEYS_AND_FEATURES.md`) and the
   stalled prompt exist; "widen the search after a tap" can be a kind A receipt once generic retune exists.

## 6. The 11 journeys and the menu rules vs `redesign-places.ts`

Checked: `src/lib/journey/menu.ts` (`MENU_RULES`, `menuMode`), `src/lib/nav/places.ts`, `src/lib/nav/redesign-places.ts`.

What does not conflict:
- `redesign-places.ts` reuses legacy tabs through `legacy(href)`, so each reused tab keeps its `menuKeys` and the same
  show, locked, hide rules. `RedesignNav` receives `locks.mode = menuMode(...)`, so all 7 modes still apply.
- Journeys map to modes, not to tabs, so adding or renaming tabs does not break any of the 11 journeys. Not found:
  any journey-specific code in the redesign nav.

What conflicts or is missing:
1. **New redesign tabs have no `menuKeys`, so they show in every mode.** These are `tab()` entries: Improve your search,
   Résumé, Why hire me, Career story, What recruiters see, Privacy, Money help, Benefits and deadlines, Scam watch.
   Their old legacy homes could carry mode rules (not checked tab by tab), so the redesign may show more in Landed or
   Time off than before. Decide per journey, or add `menuKeys`.
2. **`benefits` rule vs money opt-in.** `MENU_RULES.benefits` hides "Money and benefits" for STAYING and LANDED. The
   redesign's Finances and benefits place is shown for every journey whenever `moneyHelp !== false`. The two rules can
   disagree for Managing my career, Promotion (before applying) and Landed. The owner's decision (money is opt-in, for
   every journey) wins; remove the hide from `benefits` or stop using it for the redesign.
3. **Jobs strip for the 4 non-search journeys.** `Find a job` is locked in STAYING, PORTFOLIO and LEAVE (and EXPLORING),
   so "Better jobs for you" has no page for Growing, Fractional, Time off and, until they say ready, Entrepreneur.
   Section 5, idea 3 is the fix. Today Jobs place still lists Reviews and raises (employed only), Build your case
   (shown only in STAYING) so those journeys keep a home in Jobs.
4. **Pillar order vs places.** `PILLAR_ORDER` (for example PORTFOLIO puts "Work now" first, STAYING puts "Manage your
   career" first) has no counterpart in the redesign, where places are fixed. Fractional's "Work now" (Interim work,
   EQoverIQ) lives only inside `Find a job` `alsoMatches`, so a Fractional member whose Find a job is locked cannot
   reach interim work from the new menu. Check on screen.
5. **Learn.** `Know yourself`, `Career story` and `Other roles you could do` have no mode rules except what `legacy`
   carries; Career story is shown to all 11 journeys. That is probably right, but is not decided.
6. **`statusUnlock` copy** names "Find a Full-time Job" and "interview practice", which the redesign renamed. The
   "Turn on more tools" box is not part of any strip; one home for "has anything changed?" is not yet decided.
7. **Phone bar.** `MOBILE_TAB` has `plan`, `jobs`, `worth`, `first90` (four tabs by mode). The redesign nav has 7
   places; no mapping found. Not found: a redesigned phone bar in `RedesignNav.tsx` for `MOBILE_TAB`.
8. **Tests.** `menu.test.ts` and `place-tabs-situation.test.ts` cover the legacy places; `redesign-places.test.ts` exists. Not found: a test that every one of the 11 journeys reaches a non-locked tab in
   each place (add one; it is the check for "11 journeys must each be served").
